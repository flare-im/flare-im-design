# Performance（2.0.0-rc.1 · P0-10 DoD 27）

真源：`spec/performance-contract.json`。两半证据：源码项证明惰性容器存在（`node tooling/check-performance.mjs`），数值预算由真实挂载测出（`website/tests/performance-budget.spec.ts`，release-check 的 `performance-budget`）。

此前只有前一半。它 grep 到 `LazyColumn`、`virtualItems` 这些词就算通过——而词存在不等于窗口真的生效。本轮把 1000 会话 / 5000 消息真挂起来数 DOM，查出两件事。

## 1. 查出来的两件事

**会话列表在宿主没有约束高度时不虚拟化。** `.im-conv-list` 声明了 `overflow-y: auto` 却没有约束自身高度，于是它在一个 900px 的容器里长到 72000px，`measure()` 读到的 clientHeight 就是整份内容，虚拟窗口覆盖全部 1000 行——契约里写的 O(visible) 悄悄不成立，而且没有任何报错。修法是让它自己兜底：`height: 100%`（父容器高度为 auto 时解析回 auto，所以只在宿主真给了盒子时生效）。1000 条渲染行数 **1000 → 21**，挂载 1414ms → 1002ms。

**消息列表根本不虚拟化，阈值是 25000。** `VIRTUALIZATION_THRESHOLD = 25_000` 让 `message10k` 场景（契约写的是「O(visible + overscan)」）实际渲染一万行。代码注释写明了原因：窗口用固定行高估算，而聊天行的高度随富文本、媒体、引用变化，翻页时滚动条会跳。

这条**不改实现**：在 RC 里重写时间线的窗口与滚动锚定，风险远大于收益（原则 14 / 15）。改的是契约——把「组件保证 O(visible)」换成它真正的保证：**组件渲染宿主加载了多少就有多少，边界属于宿主的分页窗口**。于是预算落到每行的 DOM 成本和宿主该保持的窗口大小上，而不是一句守不住的承诺。

## 2. 数值预算（1440×900，dev server）

| 场景 | 预算 | 实测 |
|---|---|---|
| 会话列表 1000 条 · 渲染行数 | ≤ 60 | 21 |
| 会话列表 · 每行节点 | — | ~15 |
| 会话列表 · 滚动容器自约束 | 必须 | 是 |
| 消息列表 5000 条 · 每行节点 | ≤ 40 | ~23 |
| 消息列表 · 宿主加载窗口 | ≤ 400 条 | 见下 |
| 两份列表满载挂载 | ≤ 6000ms | 704ms |

2026-09-15 复测（Round 5）：挂载一度退化到 7.2 秒——Round 3、4 的网站回归命令带 `--grep-invert "@perf"`，这条用例没有跑到。两个原因：每条消息都预先建一个菜单 popover（Round 4 的 `FlareActionMenu` 包住气泡），每个气泡的时间标签每次都新建两个 `Intl.DateTimeFormat`。现在菜单在第一次打开时才挂载，格式化器按语言缓存，挂载 704ms，每行节点约 23。

上限都留了机器噪声的余量：它们要拦的是**性质的退化**（窗口被关掉、一行的节点数翻倍），不是毫秒数的浮动。

5000 条消息 = 116678 个节点（2026-09-15；09-13 为 171678），是压力载荷不是日常载荷。日常载荷由宿主分页决定：参考实现用 `loadOlderMessages()` 往回翻，因此 DOM 大小等于用户翻了多少页。契约把这条写成宿主约束 `hostMaxLoadedMessages: 400`，第二条用例按这个数验一遍。**宿主若无上限地累积已加载消息，DOM 也会无上限地涨**——这是当前设计下宿主必须自己守的边界。

## 3. 四端的惰性容器

| 平台 | 会话列表 | 消息列表 |
|---|---|---|
| Vue | 自写窗口（>200 条启用，overscan 8 行） | 原生布局，见上 |
| Flutter | `ListView.builder` | `SliverChildBuilderDelegate` |
| Compose | `LazyColumn` | `LazyColumn` |
| iOS | `List` | `LazyVStack` |

三个原生端用的是框架自带的惰性容器，天然按可视区构建；门禁按源码项校验它们仍在。Vue 是唯一自己实现窗口的一端，也因此是唯一测得出「窗口有没有真的生效」的一端。

## 4. 没覆盖的

- 真机 / 模拟器上的帧率与滚动流畅度：本轮只有 DOM 结构与挂载耗时，没有 60fps 证据。
- 媒体解码、上传进度的逐项更新：契约里有原则（`manyImages` / `uploadQueue`），只有源码项证明，没有测量。
- 三个原生端的渲染行数没有实测，只有「用了惰性容器」的源码证明。
