## 4. Web Live

`web-live-sdk`：真 Chromium → 真 web app（dev server 127.0.0.1:1430）→ 真 client SDK（wasm）→ 本地 Flare core 服务端（网关联调签发，仅限本地），无 mock、无网络拦截。每次运行一个 `release-live-<时间>-<uuid8>` runId，旧消息不可能满足新断言。

覆盖：两个隔离账号登录；打开会话；A→B 与 B→A 文本，逐条等 ACK（sent / delivered / read，非 failed，带稳定 `data-message-id`）；跨用户已读回执；三连发顺序；置顶 / 取消置顶；标未读 / 已读；桌面与手机视口无横向溢出；reload 后重新打开会话，桌面发出的每条恰好出现一次且 id 不变；零运行时错误。报告带 `LIVE_BACKEND=true`、`LIVE_SEND=true`、`SDK_MOCK=false`、`NETWORK_INTERCEPT=false`、计数、ACK / 接收 / 已读延迟摘要、浏览器与 wasm 构建号、`candidateId`；失败时也写 FAIL 报告与事件时间线。不覆盖：媒体、离线、SDK 重连与重复投递注入（不属于设计 kit 2.0 契约）、原生端。

冻结前在同一环境连续通过两次（断言经变异体验证：打乱顺序、重复一条、跳过重开会话，三个变异体都红）。本候选的结论以 A / B 内的 `web-live-sdk` 为准。服务端指纹在 `artifacts/release-2.0/live-sdk/environment.json`（flare-im-core HEAD、各服务二进制哈希、profile、tenant；不含任何 token / 密码）。

## 10. Security

**本轮认证挖出一个真实的 High 级缺陷，已修：多图消息「下载」的存储型 XSS。** `utils/browserDownload.ts` 把消息内容里的地址交给 `<a download>.click()`；`download` 属性对 `javascript:` 不生效，于是一条多图消息里的 `javascript:` 地址在收件人点「下载」时在宿主页面的源里执行。复现：打包后的 kit 装进 clean consumer，Chromium 里点击后 `document.title` 被改写、页面全局变量被置位。修复：`downloadableHref` 只放 http / https（含相对当前页面的路径）与本页创建的 blob，其余既不 fetch 也不点击；同一探针复测不再执行。回归测试用 `spec/security-boundary.json` 的 14 条恶意向量逐条断言（修复前 12 条红）。根因之一是门禁盲区：`check-security-boundary` 只读模板里的 `:href`，脚本里造 anchor 看不见；现增加 `scriptedNavigation` 登记，修复前的代码会被它拦下。详见 [security-boundary.md](security-boundary.md) §4b 与 [migration/2.0-rc-to-2.0.md](migration/2.0-rc-to-2.0.md) §4m。

其余：markdown-it `html: false`；3 处 `v-html` 白名单；2 个自跳转组件与 1 处脚本跳转都过闸；四端 URL 闸 × 18 向量；无动态代码执行；网络调用 3 处且都只请求宿主给的地址；无遥测依赖；clean consumer 运行时依赖树（59 个包）`npm audit`：critical 0 / high 0 / moderate 0 / low 0。未覆盖且非 kit 能解决：`<img src>` 指向攻击者服务器会泄漏浏览时机与 IP，属宿主 CSP / 媒体代理。

在 A / B 通过前，安全结论以 A / B 内的 `security-boundary` + `security-audit` + `package-certification` 为准；存在未修复的 Critical / High 即无条件 NOT READY。
