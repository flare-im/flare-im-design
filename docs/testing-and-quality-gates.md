# Testing and Quality Gates

Run the repository-wide deterministic gate from `flare-im-design`:

```bash
npm run check
```

The design-system orchestrator validates repository scope, removed paths, spec validation, zero signature drift, generated tokens, theme contracts, component layers, dependency direction, exports, accessibility, component contracts and maturity, documentation, examples, raw token use, localization, gallery coverage, visual contracts, performance, resource lifecycle, and the production website build.

## Stable Release Check

Run `npm run release:check` for package tests/builds, website visual/interaction tests, independent consumers, five Core reference apps, package content inspection and diff checks. The real Web browser suite runs on an isolated port (1499 by default; override PLAYWRIGHT_PORT). Per-check logs, partial-results.json and result.json are written to a printed temporary evidence directory.

The command fails closed if any subprocess fails, the readiness matrix has blocking rows, or evidence is unresolved. `--only=...` is diagnostic and always returns NOT_READY. A contract-only check or successful compilation cannot certify the entire release.

Physical VoiceOver, TalkBack and hardware performance are MANUAL_RELEASE_GATE. Large text, keyboard, contrast, motion, simulator gestures and resource behavior require executable automation, not a manual exemption.

## Platform validation

| Platform | Required checks |
|---|---|
| Vue | unit/component tests, typecheck, all-SFC compilation, package build, package dry-run |
| Flutter | analyze, widget/golden tests, package dry-run, example web build |
| Android | unit tests, lint, release assemble/AAR, Compose example assemble |
| Apple | Swift package resolve/test/build, SwiftUI example build |
| Website | VitePress production build and Playwright visual regression |
| Consumers | clean import/build checks from `tests/consumers` |

`npm run generate` must run before the full gate. Focused tests should run while editing; the complete matrix runs before release. Tests are not removed or weakened to make a gate green.

## Ratchets

Reviewed baselines prevent existing debt from increasing. Reductions are committed immediately so debt cannot return. The normal signature baseline is `{}`; a platform difference must be explicit in the current component contract rather than hidden in a tolerance file.

Visual baselines cover representative component and theme scenarios instead of multiplying every component by every platform, brand, mode, and viewport. Native device evidence supplements these deterministic fixtures.

## Traps that make a green suite lie

Each of these produced a false result in this repository, was found by doing something outside the suite, and now has a written rule.

**A hand-written test double rots silently.** The web app's store moved from raw `invoke("op", json)` to the typed `im` wrapper. The two test files that fake the SDK module list their members by hand, so the store's new calls landed on `undefined` and 25 tests went red — but only when someone ran them; the change itself passed every gate the repository runs, because no gate runs the app's unit tests. Two rules follow: a double of a module the code calls through must be kept in step with that module in the same change, and a **pure** helper the code delegates to (presence mapping, reaction reading, failure classification) belongs in the double as the real function, not as a stub — a stub turns "does the mapping still hold" into "was it called".

**An inspected view tree is not a laid-out view.** SwiftUI's `AppLayoutView` measures its own box through `GeometryReader`. ViewInspector hands that reader a zero-size proxy, so an inspected tree always reads `singlePane` and a pane-mode assertion passes for the wrong reason. Anything that depends on a real measurement is tested in a hosted window (`NSWindow`/`UIWindow`) with panes that report their own appearance.

**A scroll position on macOS is not the one the test asked for.** A SwiftUI list under test settles differently than on device; assert on what the user can see (which pane, which message is visible) rather than on a scroll offset.

**A screenshot tolerance in ratios hides sentences.** `maxDiffPixelRatio: 0.002` on a 1440×900 shot allows about 2,600 changed pixels — a whole changed sentence. The application-visual suite uses an absolute `maxDiffPixels: 120` and a per-platform baseline folder; macOS baselines are never copied to Linux (`docs/release/visual-baselines.md`).

**A gate that has never been red proves nothing.** Every ratchet and contract check in this repository was reverse-validated: the counter was raised, the glyph re-introduced, the vector removed, and the gate had to fail before it was trusted.

**A performance probe measures the scene you built, not the one you described.** The web app's scale scenario claimed 1,000 conversations and 5,000 messages. The 5,000 were generated on demand only when the conversation had no seeded timeline — and every scale conversation was seeded with one message, so the deep one never existed. The burst probe then sent its 120 messages to a conversation that was not open and waited for the text to appear **anywhere on the page**, which the conversation row's preview satisfied. Both defects flattered the number: 317 ms became about 2.0 s once the timeline was really 5,000 messages deep and the assertion was scoped to it. Assert inside the surface you are measuring, and check that the fixture built what its name says.

**A generated file that counts build output is a coin flip.** `docs/repository-inventory.md` says it excludes build caches, and it skipped `.build`, `.gradle`, `.dart_tool` and friends — but not `.build-xcode`, so every iOS build changed the file count and `npm run check` failed on a stale inventory that nobody had made stale. Excluding it took the inventory from 6,945 files to 2,709: the 4,236 difference was Xcode output the document claimed not to have. A generated artefact must ignore everything a build writes, or the gate that checks it is noise.

**A gate outside every script rots.** `tooling/check-ui-reuse.mjs` — the guard that migrated app screens compose kit components — was in no npm script. Two of its expectations went stale when those screens moved to newer kit surfaces (`LocalFlareDialog.prompt`, `FlareFeedback.prompt`), so it had been failing for four rounds with nobody watching. Round 6 fixed the expectations and put it in `npm run check` (38 gates → 39). A check that nothing runs is not a check.

**A test that has only ever been compiled is not evidence.** FR-113 has two halves. The arithmetic is a JVM test (`LocatedRowPlacementTest`, reverse-validated: forcing the offset back to zero reddens the half-space case, dropping the height estimate reddens two more). The placement on screen is `MessageQuoteInteractionTest.aLocatedRowArrivesInTheMiddleOfTheViewport`, which compiles on this machine and has never run, because there is no emulator here. In a report a compiled instrumented test reads exactly like a passing one unless the sentence says otherwise, so it does not join a test count and it does not settle the question it was written for: it goes to the External Validation Steps with the pass criterion attached. "Compiled, never run" is an allowed answer to "how was this checked"; silence is not.

**An affordance nobody uses rots in every direction at once.** `onSwipeReply` sat in the three native kits for three rounds. Each kit had invented its own gesture — 20% of the row's width on Flutter, 56 points on SwiftUI, 56 raw **pixels** on Compose (about 19 dp on a 3× screen) — two of them drew no feedback whatsoever, and Compose tracked a drag offset it never painted. Nothing was wrong with any gate: no app had wired the callback, so no test could reach the code, no screenshot contained it, and the contract only said the event existed. A kit surface with no consumer is not covered by the suite that covers the kit; either wire it in a reference app, where a test can drag it, or delete it. The general rule this repository now applies to new kit vocabulary — no vocabulary without a consumer — exists because of cases like this one.

**A sweep that shares one page shares one theme.** The axe sweep scans all 149 component previews in a single page session, and the kit's theme provider reads its initial mode from `localStorage` and writes it back on every change. So a preview that switches the theme leaves the document dark for every preview scanned after it, and what the sweep measures depends on the order it happens to run in. That is how a genuine 2.47:1 contrast failure on a ghost button in dark mode (FR-117) stayed invisible: the spec passed when run alone, because then the document was still light, and failed in the full suite. When a suite-only failure appears, do not stop at "passes alone, must be load" — read what the assertion actually measured. The numbers in this one named a colour pair that no amount of machine load could have invented, and reading them turned one flaky-looking failure into 21 real ones. The sweep now pins the theme before every preview and scans every preview in both themes on both viewports, opened surfaces included — 406 scans — so the result depends on the component rather than on the running order, the width, or whether the surface needed a click.

**A fixed sleep is a guess a busy machine loses.** An iOS hosted-window test scrolled to three rows, spun the run loop 0.9 s after each and compared the offsets. Under load one scroll had not finished when its offset was read, so two targets reported the same number and the test failed — about one full run in three, while passing five times out of five on its own. It was found by attributing a red run rather than dismissing it: the batch's change was reverted and the flake stayed (1 of 3 without it, 2 of 3 with it), which is what separates "my change broke this" from "this was always a coin toss". The fix is the same one the Flutter locate test already used: spin until the thing you are waiting for actually happened, bounded by a deadline, never for a fixed number of seconds.

**A sweep that never clicks scans the button, not the dialog.** Six overlay demos on the documentation site open on a click, and the axe sweep renders a preview and scans it. For those components it has therefore been scanning the trigger: the `StartConversationDialog@desktop:dark` violation that B7 fixed was the demo's own `.trigger` button, and the two modal findings beside it were the same. Nothing about the sweep's output said so — 149 previews scanned, no failures, a number that reads like coverage. Before trusting a sweep, ask what state it scanned: a surface that needs an interaction to exist has not been looked at. The sweep now clicks an opener declared per demo and scans the opened surface as a second scan, and the first run of that found four defects, two of them critical, in components that had been reported clean for months (FR-124). A gate refuses a demo of a surface that opens whose state starts closed and which declares no opener, because the failure mode here is silence, not noise.

**A regex is not the same rule in two languages.** Porting Vue's markdown-to-plain-text pass to three kits looked like transcription until the word-boundary rules: `\w` is ASCII in JavaScript and Unicode-aware under ICU, so `__周报__已发出` keeps its underscores on SwiftUI and loses them everywhere else — the same regex, the same input, two answers. All three ports write the class out as `[A-Za-z0-9_]`, and the shared table catches the difference: putting `\w` back reddens four assertions. When a rule moves between languages, the shared table is what proves it moved rather than being rewritten — hand-write the expectations from the reference implementation's behaviour, then let the reference run them first.

**A loaded machine fails the website suite for the wrong reason.** A full `npm run test:website` run alongside a Gradle build and several node gates reported 9 failures — three axe scans, five conversation screenshots and one long-press behaviour test. Every one of them passed when the spec was run alone, and the whole suite passed 143/143 on an idle machine minutes later. Treat a website-suite failure under load as unproven: re-run it idle before believing it, and never update a baseline from a loaded run.

**A table that starts at zero cannot see a 32-bit clock.** All four kits took the typing rule's instants as a 32-bit integer, which is fine in JavaScript, Dart and Swift and wraps in Kotlin: `System.currentTimeMillis()` ≈ 1.7e12 becomes negative, so "the deadline has arrived" is never true and typing never stops. The 22-case shared table certified it, because a script whose times run from 0 to 20000 is comfortable in an `Int`. The rule now takes 64-bit instants and **every timed table runs twice — once from zero, once from base 1 767 000 000 000**; truncating the Compose deadline back to 32 bits reddens only the second run, which is exactly the shape of the bug. If a table describes something that happens in time, one of its runs has to happen at a time a real clock would report.

**A driver that asks the rule when to stop will hang instead of failing.** The typing roster's test driver prunes in a loop, asking the rule for its next expiry each time. The first reverse-validation — a rule that no longer drops an expired belief — did not go red: it spun forever, and the run had to be killed. A harness that hangs is worse than one that fails, because the failure has no message and no line number. Every prune loop in the four drivers is now bounded and asserts that a prune actually dropped something (`prune at N dropped nothing`), which turns the same break into a one-line failure.

**A test helper can fake the defect it is looking for.** The Apple presence golden test went red on four cases that looked like the SDK reading `busy` as `online`. The SDK was right: the helper that decoded the table's JSON wrote `mapValues { $0.value as Any }`, which wraps an `Any?` and keeps the Optional box, so the SDK's `string()` received `Optional("busy")` and matched nothing. When a shared table reddens on one platform only, suspect the adapter that feeds it before the rule it tests — especially where a language has an optional type the table format does not.

**"The kit has it" and "an app can use it" are different claims.** `ConversationRowData.previewKind` has had a `typing` branch on four kits for several rounds and no app had ever set it true — not from neglect, but because Swift's all-`let` struct and Dart's all-`final` class had no copy-with, so a host could not produce a row with that field changed. The branch was unreachable by construction and every test of it passed, because the tests built the row directly. Before recording a capability as present, write the line an app would write.

**A contract can declare something nothing checks.** `spec/components.json` has declared slots for eight components since the catalogue was written, and no gate ever compared them with the implementations: 33 of 120 declared slot/platform pairs did not exist, all on the three native kits, including all four of `MessageList`'s. Props and events had been checked for rounds; slots were written as intent and never given a checker. A declaration with no checker is a wish — and it reads as a fact in the catalogue, the docs and the migration guide. `check-component-slots.mjs` now checks them, and the declaration says the truth per platform so the remaining gaps are counted rather than implied.

**Reverse validation finds dead code, then finds the hole that hid it.** The first cut of the reconnect rule carried a `terminated` flag. Breaking it — deleting the flag's whole branch — left all 17 shared-table cases green, because the terminal path already reset the other two fields. So the flag was dead. Deleting it and breaking the *remaining* logic was still green, which said something worse: the table had no case where it mattered. It was missing `connected → disconnected → kicked → connected`, which is the real shape of being kicked (the socket goes first, the reason arrives after) — and without it, an interruption recorded on the way down was still standing when the next session connected, refreshing a session that had nothing to do with it. Two cases later, both breaks redden. When a deliberate break changes nothing, the code may be redundant *or* the table may be blind; check which before deleting anything.

**A test that cannot fail for the right reason is worse than no test.** The web app reloads its conversation list on any non-ephemeral event, and that reload reads presence. So an SDK spy cannot tell "the reconnect rule re-subscribed" from "the list reloaded" — the assertion would pass either way, including if the rule were deleted. The app-level test asserts only the half that is unambiguous (the typing roster is cleared on a drop, which nothing else does), and the other half is left to the shared table on four platforms, with a comment saying so. Prefer a smaller honest assertion to a larger one that is satisfied by a coincidence.

**"Lossy" is not a licence to be local.** The gateway's typing relay was documented as best-effort and ephemeral, and it was — to the subscribers on its own node. Every test it had passed, because every test built its subscribers on one node. The case that was broken (two people, two gateway instances) was the ordinary one, and no unit test could see it because the registry under test is explicitly node-local. When a component's own comments say "local", ask what the non-local case does before trusting a green suite; and add the assertion that names it — here, "a node with no other local subscriber must still tell its peers".
