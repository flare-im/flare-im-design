## 1. Purpose, scope and vocabulary

Purpose: turn "the component is hard to use" into countable, owned problems. Each entry names one real app task, the kit behaviour that got in the way, the workaround the app carries today, and the smallest kit change that removes that workaround. The log is the before-state; every fix should close an entry with a reference.

Evidence: the 2026-09-14 audits (Vue kit API, kit gates and tokens, web app, Tauri app, Flutter app, iOS and Android apps, SDK capability matrix) and the builds measured the same day against the kit working tree: web 2 TypeScript errors, Tauri 5, Flutter 7 analyzer errors, Android 22 Kotlin errors, iOS build fails.

Verification: every entry below was re-opened in the cited kit file and, where an app is named, in the cited app file. Three candidates from the audits were dropped because the claim could not be confirmed in code:

- StatusBanner "single line": all four kits wrap the text and already accept an action, so the claimed limit no longer holds.
- Web global search mis-laid by the display-contents overlay slot: the CSS is confirmed, the visual effect is not provable without a runtime session.
- Mobile shell 100dvh pushing the bottom navigation below host banners: same reason.

Class:

- DESIGN_SYSTEM: the kit API, behaviour, contract or kit documentation causes the friction.
- APP: the kit already supports the task; the app did not adopt it (the Design System change is "none (app fix)").
- SDK: the SDK or server shape causes the friction.
- PLATFORM: an OS or framework integration contract (back navigation, pickers, presenters) is missing between kit and host.
- TEST: a gate or test that should have caught the problem does not exist or does not run.
- DESIGN: a design decision (token scale, text roles) is missing or contradicts what the docs promise.

Priority:

- P0: blocks the core IM loop, is a functional defect or crash, or makes a task inaccessible.
- P1: major usability problem, or forces substantial duplication in apps.
- P2: polish or consistency.

Resolution: OPEN; FIXED (ref: commit, PR or gate); WONTFIX (why). All entries start OPEN.

## Appendix B: SDK/server gaps that look like UI gaps

1. Pinned, marked and retention message events are dropped by the binding event bridge, so a pinned bar cannot update live (`flare-im-core-sdk/bindings/shared/src/event.rs:352`).
2. The mention count exists on conversations but is never filled, so rows cannot show a mention badge (`flare-im-core-sdk/src/model/conversation.rs:505,556`).
3. There is no group member search op, so a member search box has nothing to call (SDK audit, group matrix).
4. There is no resend op; a failed message cannot be retried through the SDK (SDK audit, finding X5).
5. Standalone upload and download progress is never emitted on any binding, so a transfer progress bar cannot bind (SDK audit, gap 4).
6. Conversation delete and mark-unread are local-only and may reappear after sync (SDK audit, gap 2).
7. Group per-member read receipts are unavailable, so the read-receipt sheet works for 1:1 only (SDK audit, gap 2).
8. Message search is local-only, capped at 200 results with no pagination (SDK audit, gap 2).
9. Recall and delete-for-everyone payloads carry no reason or scope, and the server checks neither sender nor time limit (SDK audit, finding X2).
10. Token expiry is never pushed by the server and the social stack does not refresh the IM token, so a re-login banner cannot be driven by events (SDK audit, gap 5).
11. Notification preferences and storage usage have no or partial SDK APIs (SDK audit, social rows).
12. Typing is relayed only within one gateway node, so typing indicators are unreliable across nodes (SDK audit, conversation rows).
13. The social C ABI exposes IM as raw JSON only, so the three native apps hand-map every message (`flare-social/flare-social-sdk/docs/SOCIAL-C-ABI-SUPERSET.md:1-3`).
14. Translate exists only as a capability stub, so a translate action has no backend (SDK audit, message actions).
15. The core has no presentational send state, so every app re-derives sending, sent, read and failed from proto status, `conversationSeq` and `isRead` (web `host/messageStatus.ts`, Tauri `host/chat/utils/kitMessage.ts`, and the iOS, Android and Flutter mappers). The rule belongs in the core once.
16. Reaction lists read through `message.list` come from an unordered map (`flare-im-core-sdk/src/infrastructure/persistence/sqlite/message_repo/operations.rs`, `list_reactions`), so reaction pills can change order on every refresh; the snapshot writer sorts, this path does not.
17. `flare-social-vue-ui` (in the SDK repository) ships its own contact list, member list, search, profile card and report dialog with bespoke CSS instead of composing this kit. Its data and validation helpers are useful; its UI competes with the kit. Reference apps use only its helpers after Round 2.
18. The Swift and Kotlin social wrappers cannot restore an IM session from a stored token, so iOS and Android sign in on every launch.
19. The Flutter social SDK has no verification-code login, code-verified registration or password reset, so Flutter sign-up likely fails where the server requires a code.
20. Native wrappers return untyped JSON for writes, so apps cannot tell a refused write from a successful one without per-call parsing (part of Appendix A item 21).
21. Rich-text normalisation drops tables, underline and images before the document is stored, so the rich-text body all four kits draw since R9-B6 cannot show them (S25, `rich_doc_v2::from_markdown`).
22. The core has builders for polls and tasks and no op that acts on them — no vote, no voters, no status or assignee update — so the `vote` and `taskToggle` intents all four kits report since R9-B8 have nowhere to go (S26).
